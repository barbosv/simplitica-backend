# Native purchase enrollment proof

This is the implementation design for the already approved subscriber enrollment boundary. Managed-provider qualification passed; public enrollment remains unavailable until this proof path is implemented and qualified on a supported physical device. Internal D1 repositories do not verify purchase possession.

## Existing code and chosen approach

The legacy subscription sync route associates a signed transaction with a caller-supplied appAccountToken, and its D1 uniqueness includes that token. Neither those rows nor knowledge of their identifiers can establish cloud ownership. The native subscription UX also groups billing retry with grace; cloud authoring must use verified entitlement facts instead.

The chosen approach combines the qualified native identity with current, device-bound StoreKit evidence obtained by the authentic app and a challenge-bound App Attest request. Rejected alternatives are plain signed-transaction upload, account-token matching, and App Attest without device-bound StoreKit checks: each leaves copied purchase evidence insufficiently bound to the native request. These are engineering decisions under the existing one-owner/one-lineage scope, not new purchase or account-recovery permissions.

## Native signing boundary

Explicit Connect reads only StoreKit `.verified` current entitlements and an independently verified AppTransaction. It accepts no imported JWS, caller transaction, caller device identifier or arbitrary signing payload. Select the configured auto-renewable subscription product and store environment; unverified results, unsupported proof fields or ambiguous ownership fail closed while keeping local app use available. Current entitlements cover subscribed/grace subscriptions and omit revoked/refunded purchases. [Apple current entitlements](https://developer.apple.com/documentation/storekit/transaction/currententitlements.md)

Use the actual `AppStore.deviceVerificationID`. Require deviceVerification and deviceVerificationNonce on both app and transaction JWS, and on native-submitted StoreKit renewal JWS used in the device-bound enrollment proof. Authoritative App Store Server API renewal facts instead require signature, environment and lineage checks and need not contain these additional StoreKit device fields. Missing, malformed or mismatched required native fields deny enrollment. Compare the signed device verification value to SHA384 of lowercased nonce UUID followed by lowercased device UUID. Require the app and subscription proofs to carry matching signed appTransactionId values; this stable account/app identifier adds binding but is not a secret or possession proof. [Device verification](https://developer.apple.com/documentation/storekit/appstore/deviceverificationid.md), [app transaction identifier](https://developer.apple.com/documentation/storekit/apptransaction/apptransactionid.md)

The app signs one fixed versioned enrollment action, never arbitrary data. Its canonical payload includes server challenge, verified-native session binding, app/environment, attested device key identifier, actual device-verification identifier, and SHA256 hashes of the exact app/transaction/renewal JWS values. Encode fields in a prescribed ordered representation shared by Swift and TypeScript golden fixtures; do not rely on language-specific JSON key order. Restore/refresh operations that can prompt App Store authentication follow an explicit user action.

## Server verification and commit

Issue 32 random challenge bytes, retain only their SHA256 hash, expire within 5 minutes, and bind to exact native identity, enrollment action, app/environment and device key. The native token must validate cryptographically for the native client/audience/scope; the ChatGPT token cannot enroll a device. Bound request size and acquisition time and avoid request-body/error logging.

Verify App Attest certificate chain and nonce, app identifier/environment, credential/public-key binding and assertion signature/counter. Persist a key only for one owner; advance counters atomically with consuming challenges. Keep development and production attestations separate. Exact validation follows Apple's server guide and captured compatible fixtures, including required authenticator extensions. [Apple App Attest server validation](https://developer.apple.com/documentation/devicecheck/validating-apps-that-connect-to-your-server.md)

Independently verify Apple signatures, bundle/app ID, environment, product, original transaction lineage, device bindings and matching appTransactionId. Use the existing official Apple verifier's app/transaction/renewal verification methods; explicitly validate device fields absent from its current TypeScript transaction model only after signature verification. A body appAccountToken cannot override a signed field. Require current active/trial entitlement or signed unexpired grace; billing retry alone, expired or revoked facts cannot authorize authoring. Verify renewal lineage and signed-date ordering rather than trusting an unverified renewal blob. At enrollment, fetch authoritative Apple subscription status over the fixed authenticated App Store Server API and verify its signed facts. Cache authoring eligibility for at most 5 minutes from successful server refresh, never from a caller timestamp; refresh when older, and deny authoring if freshness cannot be established. Refund/revocation notifications can deny sooner. A signature or unexpired transaction alone is not proof that a purchase remains current. [Apple subscription statuses](https://developer.apple.com/documentation/appstoreserverapi/get-all-subscription-statuses.md)

The eventual commit batch must consume the exact challenge, advance the expected attestation counter, and create owner/business/device plus unique purchase lineage atomically. Before rejecting a consumed challenge or old assertion counter, authenticated owner-scoped lookup may return the prior receipt only for the exact committed canonical request, including original proof hashes and assertion binding. This replay path performs no new ownership/counter mutation; changed evidence needs a fresh challenge/proof. Public integration must extend the internal foundation ledger to bind this full proof fingerprint; the initial logical evidence tuple alone is insufficient at the public boundary. Competing identity/device/lineage claims leave no partial owner rows and never reassign ownership. Additional-device attachment and lost-device recovery need explicit owned proof paths; a new local appAccountToken is not account recovery authority.

## Trust boundary and release evidence

Sign in with Apple identity and the App Store purchasing account are separate concepts. Enrollment explicitly associates a holder's two proofs; it does not claim that Apple exposes a common identifier for them. The server also has no documented independent hardware cross-proof between App Attest and StoreKit deviceVerificationID. Copied-JWS resistance relies on the authentic native app's restricted OS-backed signing path. A compromised-device signing oracle remains a residual risk; do not describe this as absolute hardware identity verification.

Physical-device qualification must cover development App Attest, sandbox StoreKit proofs, matching IDs/device hashes, altered JWS/device ID/action/session rejection, replay/counter races, competing owners and notification entitlement changes. Pin development AAGUID behavior to supported captured evidence: current Apple documentation has differing development spellings across pages, so do not guess or allow broad aliases. Missing/mismatched fields, unsupported attestation, or Family Sharing ambiguity do not fall back to plain JWS. Preserve local app use and offer recovery guidance. No real purchase, account creation, production binding, production migration or rollout is authorized by this design.

This source review establishes a proposed protocol and explicit trust assumptions, not live StoreKit/App Attest qualification. The existing 20 passing native authentication tests cover a different boundary.
