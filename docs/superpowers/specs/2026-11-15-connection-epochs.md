# Issuer-bound connection epochs

The account foundation's revision compare-and-swap prevents stale native commands from undoing disconnects. Its timestamp fence alone cannot prove that an OAuth credential belongs to a new connection: a delayed time sample or backward clock can admit a JWT minted while disconnected. Public cloud authorization remains blocked until this design is implemented and qualified.

## Selected protocol

Keep Auth0 and avoid Enterprise, as requested for the small family/friends audience. Use authorization-code-only ChatGPT sessions with an initial development target of 24 hours; after expiry, sign in again through the normal OAuth UI. Native iPhone refresh remains separate and enabled. The Enterprise refresh-metadata approach was considered and rejected as a paid dependency. This access-only ChatGPT path requires live expiry/reauthorization qualification.

Use the connection's durable D1 revision as an issuer-signed epoch. Time checks remain auxiliary validation. An access token must carry numeric `https://simplitica.co/connection_epoch` equal to the currently active connection revision, with the approving device still active and owned. Missing, malformed or old epochs deny access even when the token otherwise validates and its iat is recent. The epoch comes only from the verified signed JWT, never model parameters, a request body or a lookup substituted by the resource server.

On initial cloud OAuth authorization, the scoped Auth0 Action asks an authenticated, bounded development backend hook for the active epoch and external authorization namespace using its trusted Apple identity. It writes both into the access token. The MCP client permits only authorization-code grants, its API disables offline access and the ChatGPT configuration omits offline_access. Independently, the scoped Action denies every MCP refresh, missing protocol and unsupported protocol regardless of scopes; no previously issued refresh credential can acquire the current epoch. Native first-party refresh behavior is unchanged.

Reconnect increments the D1 revision, so prior access tokens stay denied. An already-started interactive authorization may complete after fresh native approval if its issuance-time lookup sees the active new revision and verifies the same owner; this is an explicit policy choice. It is a new authorization, not renewal of an old access/refresh token. A lookup performed before disconnect retains the old epoch and is denied even if signing finishes later. Fresh issuance after approval is permitted in the same integer second and after a backward-clock reconnect; an earlier elevated legacy timestamp cannot strand the new epoch.

OpenAI documents authorization-code+S256 and authentication challenges that rerun OAuth; actual ChatGPT expiry behavior without a refresh token must still be observed. No provider discovery rewriting, custom authorization server, paid feature or iat-only fallback is permitted. [OpenAI authentication](https://developers.openai.com/plugins/build/auth), [Auth0 API lifetime](https://auth0.com/docs/secure/tokens/access-tokens/update-access-token-lifetime)

## Scope and isolation

Only the exact third-party development MCP client/audience and initial requests for `cloud:access` use the epoch lookup. Synthetic `probe:read` authorization still works, but its MCP client also becomes access-only. Native `qualification:read` login and native refresh remain unchanged. Native tokens, superseded first-party clients, wrong resources and untrusted identity metadata cannot issue cloud epochs. Every MCP refresh grant is denied, even if a legacy grant exists or scope fields are omitted. Cloud access needs a new authorization-code flow.

The hook is an application-state lookup, not an OAuth server. It issues no tokens and grants no ownership. Its service credential is separate from the Auth0 client secret, scoped to this read-only development endpoint, stored only in development secrets, and never logged. The hook fixes issuer/client server-side; the bounded body contains only the trusted opaque Apple identity. It returns an active epoch or a fixed inactive result, without personal identifiers, tokens or database errors. No new public route or deployed binding is added during internal implementation.

## Admission and failure behavior

The resource server cryptographically verifies RS256, exact development issuer/MCP audience/third-party client, exp, nonempty subject, trusted Apple claim, safe iat and `cloud:access`, then passes the signed epoch to D1 authorization. Active status, exact epoch and active owned device are checked together. The approval-time `iat` cutoff is superseded: admission never compares `iat` with approval time or the legacy stored `token_not_before` field. Safe-integer, nonnegative and not-future `iat` validation and normal `exp`/`nbf` checks remain required. The legacy field may remain populated for schema compatibility, without authorization authority. Future domain mutations recheck that same epoch/status and paid entitlement inside their atomic write batch; an earlier authorization read is not a durable permission.

The epoch claim is a positive safe integer; the namespace claim must exactly match canonical externally configured base64url 32 bytes. Inactive/mismatched state, refresh or ambiguous protocol, missing hook credentials, redirects, oversized/invalid responses, timeouts and hook failures deny cloud issuance. There is no refresh/session/profile metadata dependency or automatic rebasing. Safe audit records contain only fixed labels and booleans.

The hook compares its fixed-format service credential without timing-sensitive string equality, limits body/read duration and returns no-store JSON. The Action uses a fixed HTTPS development URL, no redirects, a two-second total fetch/read deadline and a one-KiB response cap. Native approval still requires fresh proof binding expectedRevision into the canonical command; issuer epochs do not replace native purchase/device verification.

## Required evidence

Real workerd/D1 tests cover same-second native approval/private-hook lookup/RS256 issuance and repeated admission of the identical token until expiry or revocation, elevated legacy timestamps with a backward-clock reconnect, old/current signed epochs, wrong owner/client/device, delayed initial issuance, disconnect/reconnect and tokens minted during disconnection with misleading iat values. Real signed-JWT fixtures must prove the resource server cannot replace a missing/old epoch with a current database value. Tests execute the exact Action artifact with a bounded HTTP hook fixture and verify initial issuance, unconditional refresh/unknown-protocol denial and redacted failures.

Before public cloud use, qualify actual Auth0/ChatGPT authorization without refresh, expiry, authentication challenge, new sign-in, disconnect and fresh native reapproval. Temporarily shorten only the development API lifetime for expiry testing, then restore its normal target. Do not enable cloud access if the client requires unsupported refresh behavior. No public authorization, production resource, migration or release is implied by local fixture success.

## Restore and deployment namespace

`createCloudTokenAuthorizer` requires trusted `CLOUD_AUTHORIZATION_NAMESPACE` configuration outside D1, canonical unpadded base64url for 32 bytes. The signed claim `https://simplitica.co/authorization_namespace` must match before data lookup. A copied/restored database with the same numeric revision cannot revive an old token under a different namespace. Namespace and epoch are captured as one immutable hook result; they cannot be taken from separate mutable configurations or mixed across an await.

Cold restore/replacement/cloning is unsupported while serving traffic. Enter maintenance for both issuance hooks and cloud APIs; drain in-flight lookups; revoke all restored connections and device attestations; rotate the namespace outside the restored database; deploy every instance with the new namespace before restoring traffic. Require fresh native enrollment/approval and new OAuth authorization. Never reuse namespace values or preserve restored active authority. Old access tokens fail namespace comparison and old refresh credentials remain denied. Native signed command payloads must also bind the namespace to prevent replay after counter/challenge restore. This is a mandatory future operational release procedure, not an automatic production action.
