# App Attest verification boundary

This implements the cryptographic portion of the approved native enrollment design. It grants no cloud ownership or authoring access and adds no public endpoint. Physical-device qualification and the StoreKit possession path remain required before public enrollment.

## Approach and source evidence

Reuse pinned `node-app-attest@2.2.0` cryptographic verification behind a bounded project adapter. Writing new signature algorithms or relying on the package without additional checks were rejected: the package handles Apple signatures, but source review found missing certificate validity/usage constraints and strict decoder policy. Lock the reviewed `cbor2@2.4.2`, `pkijs@4.0.1` and `asn1js@4.0.0` dependencies. Workers compatibility must be proved under the existing compatibility date and flags, not inferred from the package's Node 24 requirement. [Package manifest](https://raw.githubusercontent.com/uebelack/node-app-attest/v2.2.0/package.json), [Workers crypto support](https://developers.cloudflare.com/workers/runtime-apis/nodejs/crypto/)

The package checks Apple-root signatures, nonce, RP ID, key/credential binding, initial counter and environment markers. The adapter must additionally enforce ordered certificates, validity at server time, CA/leaf and key-usage constraints, bounded inputs and exact configured environment; allowing development upstream also allows production. No provider error text may escape. The App Attestation root is distinct from the StoreKit roots and is pinned from Apple's published certificate. [Verifier source](https://raw.githubusercontent.com/uebelack/node-app-attest/v2.2.0/src/verifyAttestation.js), [Apple root](https://www.apple.com/certificateauthority/Apple_App_Attestation_Root_CA.pem)

The internal attestation verifier accepts the exact client payload bytes (at most 8 KiB), rather than a precomputed clientDataHash. Pass those bytes unchanged to upstream’s Uint8Array challenge input, which computes SHA256 internally; the native client supplies the same hash to App Attest. This preserves the prescribed nonce calculation without a hash preimage, upstream patch or alternate algorithm.

## Parsing and policy

Before any library decoder, bound decoded attestation to 64 KiB, assertion to 8 KiB and exact signed client payload to 8 KiB. Use strict CBOR with depth 16, duplicate-map rejection, definite-length containers, safe integers, no floats/bignums/tags/undefined, expected map/array/byte-string shapes and no trailing objects. The authenticator's embedded COSE/extension objects receive the same bounds and policy. Do not normalize strings, convert arbitrary object keys, accept malformed Unicode or expose global decoder registries. Use maintained ASN.1/X.509 parsing, not handwritten certificate or ECDSA DER parsing. [CBOR decoder controls](https://raw.githubusercontent.com/hildjj/cbor2/v2.4.2/src/options.ts)

Separate cryptographic facts from application admission policy. Internal fact extraction may test older genuine Apple-signed attestation fixtures that lack current extensions; it is not a complete enrollment verifier. The strict admission wrapper requires configured team/bundle/environment and explicit accepted app validation categories/build versions, including required authenticator extensions. Future public enrollment imports that strict wrapper, not a permissive legacy-fixture helper. No environment variable or request field can disable admission checks. Missing current-policy evidence fails closed; the device capture determines supported behavior rather than broad aliases or fallback validation.

Certificate checks must validate the supplied leaf/intermediate order and the exact pinned root chain, certificate times, CA/leaf roles, relevant key usage, supported EC/signature algorithms, expected nonce-extension shape and public-key consistency. Unknown critical certificate extensions cannot be silently ignored. Keep the checks compatible with genuine Apple fixture constraints; a mismatch is investigated rather than suppressed. Attestation environment must equal the trusted configured environment exactly.

## Assertions and atomic integration

For exact payload bytes `P` and authenticator bytes `A`, reconstruct `clientDataHash=SHA256(P)` and `nonce=SHA256(A||clientDataHash)`. The reviewed upstream fixture verifies with Node's `verify("sha256", nonce, key, DER_signature)` or WebCrypto ECDSA/SHA256 with `data=nonce`; using `A||clientDataHash` directly fails that fixture. Do not accept both algorithms. This is upstream interoperability evidence; the fixture's key does not match the published attestation fixtures, so it is not independently proven paired-device evidence. [Assertion source and fixture](https://raw.githubusercontent.com/uebelack/node-app-attest/v2.2.0/test/verifyAssertion.test.js)

Require correct RP ID, exact client action/challenge context, permitted authenticator extensions and an increasing unsigned counter. The upstream path reads signed int32, so fail closed and require key rotation before its supported counter range is exhausted; never wrap/reset counters. Accept stored public keys only from prior verified attestations, not request-supplied keys. Cryptographic verification returns facts; challenge consumption, expected lifecycle revision, counter advancement and domain mutation must later commit in the same D1 batch. A separate earlier counter write followed by an unguarded lifecycle write is insufficient.

Public native actions use prescribed canonical UTF8 bytes shared with Swift golden fixtures. The payload binds action/version, externally configured authorization namespace, fresh server challenge, exact owner/session context, attested key, application/store environment, lifecycle expectedRevision when applicable, and exact purchase-proof hashes for enrollment. A failed compare-and-swap cannot silently rebase to a new revision and reuse the original signed intent.

## Verification and release gates

Use actual workerd fixtures for P256 leaf/P384 issuer verification, certificate-time rejection, decoder bounds, altered nonce/RP/key/environment, unsupported algorithms/extensions, DER handling and counter boundaries. Historical fixture clocks are injected only into internal verification dependencies for deterministic tests; public services use server time. Current-time verification must reject expired historical leaves. Preserve fixture source/tag/license and distinguish Apple-root-signed fixtures from synthetic parser/signature cases.

Capture a fresh development attestation and assertion from the same supported physical iPhone/key. Validate the Apple chain, expected team/bundle, exact AAGUID/extensions and assertion algorithm in workerd using that matched key; keep raw device proofs/receipts in protected ignored evidence, out of chat, logs and commits. Existing native authentication 20-test evidence is a different boundary. The owner has confirmed an iPhone is available; no device attestation has yet been captured.

Do not claim independent App Attest-to-StoreKit hardware cross-proof, current purchase entitlement or production readiness from this adapter. The restricted native signing path, authoritative Apple status refresh, complete-proof replay fingerprint, device enrollment/recovery and production rollout remain governed by the native purchase enrollment design.
